# WMS — прототип інформаційної системи управління складом

Прототип за курсовою роботою «Проєктування WMS». Код відповідає моделі: вимоги FR/NFR, прецеденти UC-01…UC-08,
класи Boundary–Control–Entity, діаграми послідовності. Демо-дані узагальнені, без прив'язки до реальної компанії.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2, Alembic, Pydantic v2 · PostgreSQL 16 · outbox + фоновий воркер ·
React + TypeScript + Vite + vite-plugin-pwa · nginx (HTTP + HTTPS TLS 1.2+) · docker compose.

## Швидкий старт

```bash
docker compose up --build
```

Після запуску:

| Що | Адреса |
|---|---|
| АРМ і ТЗД (HTTP) | http://localhost:8088 |
| АРМ і ТЗД (HTTPS, потрібен для камери телефона) | https://localhost:8443 (самопідписаний сертифікат — прийміть попередження) |
| ТЗД напряму | http://localhost:8088/tzd |
| API (Swagger / OpenAPI 3) | http://localhost:8010/docs, http://localhost:8010/openapi.json |
| Перевірка стану | http://localhost:8010/health |

Порти можна змінити змінними `WMS_HTTP_PORT`, `WMS_HTTPS_PORT`, `WMS_API_PORT` (наприклад, `WMS_HTTP_PORT=9000 docker compose up`).
Сервіси: `db` (PostgreSQL 16), `api` (FastAPI; під час старту застосовує міграції Alembic і заповнює демо-дані),
`worker` (надсилає події з outbox у mock ERP і mock служби доставки), `web` (nginx + PWA), `backup` (pg_dump кожні 15 хв).

Повне скидання даних: `docker compose down -v && docker compose up --build`.

### Локальний запуск без Docker

```bash
cd backend
py -3.12 -m venv .venv            # Linux/macOS: python3.12 -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt      # Linux/macOS: .venv/bin/pip
.venv/Scripts/python -m app.seed                       # SQLite wms.db + демо-дані
.venv/Scripts/python -m uvicorn app.main:app --port 8010
.venv/Scripts/python -m app.worker                      # в окремому терміналі
```

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, проксі /api → http://localhost:8010
```

Для PostgreSQL задайте `DATABASE_URL=postgresql+psycopg://user:pass@host:5432/wms`. Mock ERP/доставки в такому режимі
живуть у самому API (`ERP_URL=http://localhost:8010/mock/erp`, `DELIVERY_URL=http://localhost:8010/mock/delivery`).

## Наскрізний сценарій для демонстрації

1. **Приймання (UC-01):** `receiver` → ТЗД «Приймання» → `ASN-0001` → партія `L2702D`, кількість `90` → скан `4820000000017`
   → … → «Завершити приймання». Недостача → акт розбіжностей (ВП-03), етикетки SSCC на вантажні одиниці.
2. **Розміщення (UC-02):** `driver` → «Розміщення» → скан SSCC етикетки (або кнопка завдання) → ТЗД показує комірку → скан адреси комірки.
   Інша комірка → запит підтвердження заміни.
3. **Залишки (UC-07):** `sales` → «Доступні залишки» → `молоко` / `P-001` / GTIN; помилка в назві (`малоко`) → схожі позиції.
4. **Комплектація (UC-03):** `manager` → АРМ «Замовлення і хвилі» → «Сформувати хвилю»; `picker` → ТЗД «Відбір» → «Отримати завдання»
   → скан комірки → скан товару (не той товар — блокування).
5. **Відвантаження (UC-04):** `packer` → ТЗД «Контроль і відвантаження» → скан товарів → «Відвантажити» → SSCC, рампа, слот;
   воркер створює заявку в mock службі доставки і записує ТТН (АРМ «Відвантаження»). Вимкніть mock доставки в АРМ «Інтеграція» —
   заявка стоїть у черзі й надсилається повторно після ввімкнення (4а).
6. **Інвентаризація (UC-05):** `manager` → «Інвентаризація» → план для зони або комірок з порогом; `counter` → ТЗД «Перерахунок»
   (сліпий підрахунок); розбіжність понад поріг → повторний перерахунок; затвердження — лише `manager` (BRL-02).
7. **Звіти і KPI (UC-06):** `accountant` → «Панель KPI» (оновлення кожні 10 с), «Звіти» ВП-01…ВП-06, експорт XLSX/PDF.
8. **Довідники і ролі (UC-08):** `manager`/`admin` → «Довідники»; `admin` → «Користувачі і ролі»; усе пишеться в «Журнал».

## Етикетки і штрихкоди

| Об'єкт | Символіка | Приклад |
|---|---|---|
| Товар (GTIN) | EAN-13 | `/api/barcodes/ean13/4820000000017.svg` |
| Адреса комірки | Code128 | `/api/barcodes/code128/ST-01-02-1.png` |
| Палета / вантажне місце | GS1-128 з AI (00), SSCC 18 цифр з контрольною цифрою | `/api/barcodes/sscc/048200000000000017.svg` |
| Номер завдання | QR | `/api/barcodes/qr/PICK-000001.svg` |
| Товар + партія + термін | GS1-128 з AI (01)(10)(17) | `/api/barcodes/gs1/(01)04820000000017(10)L1(17)271231.svg` |

Ендпоінт `GET /api/barcodes/{ean13|code128|sscc|gs1|qr}/{значення}.{svg|png}` публічний (зображення кодує лише передане значення)
і перевіряє контрольну цифру GS1 (невірна → 422). `GET /api/barcodes/validate?code=…` розбирає скан.

**Друк етикеток:** АРМ → «Етикетки» → позначте товари і/або комірки, вкажіть кількість нових SSCC для палет → «Переглянути» →
«Друк із браузера» (меню і кнопки ховаються при друці) або «PDF-аркуш» (A4, 3 × 7 етикеток 70 мм, reportlab,
`POST /api/barcodes/sheet`). Етикетки SSCC вантажних одиниць після приймання — у результаті приймання на ТЗД і
`/api/receiving/labels/{sscc}/print`; пакувальний лист і етикетка відправлення — АРМ «Відвантаження».

## Сканування

* **USB/Bluetooth-сканер** працює як клавіатура: поле сканування на ТЗД завжди у фокусі, Enter завершує скан.
  Підтримуються GTIN-8/12/13/14, SSCC-18, рядки GS1 з AI у дужках `(01)…(10)…(17)…(37)…` і без дужок з роздільником GS
  (`\x1d`) або `|`. Під полем одразу видно результат перевірки: «✓ GS1 …» або «✗ Невірна контрольна цифра GS1».
* **Камера телефона** (кнопка «Камера», бібліотека html5-qrcode: EAN-13/8, UPC-A, Code128, QR, DataMatrix).
  Браузер дає доступ до камери лише в безпечному контексті, тому з телефона відкривайте HTTPS:
  1. Телефон і комп'ютер в одній Wi-Fi мережі; дізнайтесь IP комп'ютера (`ipconfig` / `ip a`), напр. `192.168.1.20`.
  2. Дозвольте вхідні з'єднання на порт 8443 у брандмауері.
  3. На телефоні відкрийте `https://192.168.1.20:8443/tzd`, прийміть попередження про самопідписаний сертифікат, увійдіть як `receiver`.
  4. «Приймання» → `ASN-0001` → «Камера» → наведіть на EAN-13 з аркуша етикеток (АРМ → «Етикетки» → PDF, роздрукуйте або відкрийте на іншому екрані).
  5. Для комірок (Code128) — «Розміщення» або «Відбір», для SSCC — «Розміщення».
  Сертифікат генерується при першому старті контейнера `web` (том `certs`); для продуктиву замініть файли
  `/etc/nginx/certs/wms.crt|key` на справжні.

## Офлайн-режим ТЗД (NFR-2.3)

PWA: оболонка застосунку кешується service worker'ом, останні GET-відповіді API доступні офлайн (NetworkFirst).
Скани приймання, підтвердження відбору й результати перерахунку без зв'язку зберігаються в черзі на терміналі
(банер «Немає зв'язку… У черзі: N») і надсилаються автоматично при відновленні зв'язку. Кожна операція має
`Idempotency-Key`, тому повторна відправка не дублює дані (TC-16). Перевірка: DevTools → Network → Offline, зробіть кілька
сканів, поверніть Online. Встановлення на Android: меню Chrome → «Додати на головний екран».

## Архітектура і відповідність моделі

Трирівнева: клієнти (АРМ, ТЗД) → API-шлюз (FastAPI-роутери з перевіркою JWT і ролі) → модулі → PostgreSQL.
Шари BCE: **роутер (Boundary) викликає лише менеджер (Control); менеджер працює із сутностями лише через репозиторії.**

```
backend/app/
  entities/          Entity: моделі SQLAlchemy (Товар, Партія, Комірка, Залишок, Поставка, …)
  repositories/      РепозиторійЗалишків, РепозиторійДокументів, РепозиторійЗавдань, РепозиторійДовідників (+ журнал, outbox)
  services/          СервісПравил (rules.py: вибір комірки, FEFO, маршрут), ПублікаторПодій (events.py), GS1, штрихкоди
  modules/<модуль>/  router.py (Boundary) + manager.py (Control)
  worker.py          фоновий воркер інтеграції
alembic/             міграції
frontend/src/arm     ВебІнтерфейсАРМ;  frontend/src/tzd — ЕкранТЗД
```

## Резервне копіювання і відновлення

```bash
docker compose exec backup sh -c 'ls -1t /backups | head'      # список копій
docker compose exec backup sh /backup.sh                        # позачергова копія
docker compose stop api worker
docker compose exec backup sh /restore.sh /backups/wms_YYYYmmdd_HHMMSS.dump
docker compose start api worker
```
